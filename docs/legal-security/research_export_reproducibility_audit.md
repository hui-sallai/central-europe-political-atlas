# Research export reproducibility audit (2026-10-04)

**Question:** does a clean checkout produce deployment research-data identical to the committed `public/research-data`?

**Answer:** no. The committed public export is a stale mirror of canonical `src/data`. CI regenerates the export on every
deploy, so the **live site already serves the regenerated bytes, not the committed ones**.

## Method

1. Started from a clean tree at `5772851`.
2. Ran the exact CI export step:
   `RELEASE_COMMIT_SHA=<sha> REUSE_FROZEN_RESEARCH_OUTPUTS=1 pnpm export:research-data`.
3. Compared the result field by field with `HEAD`.
4. Downloaded the same files from the live site (deploy of `e75bbb1`, workflow run 37135919162) and compared hashes.
5. Restored the tracked files only after recording this analysis.

`pnpm build` (local release path) additionally rewrites
`src/data/analysis/advanced_analysis_validation_summary.json` (`generated_at` only). That gives 12 tracked files; an
earlier report miscounted this as 13.

## Why they diverged

- **`1a7633e` (Rename release v1.91 → v2.0):** edited the canonical `src/data` metadata but did not re-run the exporter
  for the public copies.
- **`7f609ed` (official descriptive refresh):** `data-refresh:apply` updated canonical monthly history and the coverage
  audit, plus some public high-frequency files. It did not update the public monthly-history and coverage copies that
  `scripts/export-research-data.mjs` copies verbatim from `src/data`.

## Deployment behaviour

CI runs **B**: `pnpm export:research-data` (with `REUSE_FROZEN_RESEARCH_OUTPUTS=1`) before `build:site` and deploys the
regenerated files.

**Proven** for the live deployment of `e75bbb1`: 10 of the 11 files are byte-identical to the regenerated output, and
`release_manifest.json` differs only in per-build provenance. Production has therefore served the refreshed data since
the deploys that followed `7f609ed`.

Pushing the current branch would publish the **same** research-data bytes as the live site, apart from per-build
provenance.

## Classification

- **Case B** (committed exports stale; canonical `src/data` is already-pushed production data): the four
  monthly-history and coverage files.
- **Generated metadata consequence of the v2.0 rename:** the six label files, plus `release_manifest` (which also carries
  build provenance by design).
- **Byte-only:** `advanced_analysis_validation_summary.json`.

**Not committed.** Refreshing the committed public copies requires an **OWNER APPROVAL** of the 11-file change set.

## Control added

`pnpm research-export:check` (`scripts/validation/research-export-check.mjs`) regenerates the exports from `git archive
HEAD` in a temporary directory, exactly as CI does, and compares them with the committed files. Per-build provenance in
`release_manifest.json` is excluded. It never writes to the working tree.

It currently **fails on these 11 files**. It is not yet wired into CI: it should be, after the owner approves committing
the regenerated exports, so that a future stale mirror fails CI instead of deploying silently.
